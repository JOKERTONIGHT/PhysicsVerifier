# PhysicsVerifier 项目整体结构

本项目旨在实现对于物理竞赛题模型回答的规则检查，即根据给定的物理竞赛题，检查模型回答是否存在违背物理规则的错误。

## 代码与目录总览

| 文档概念 | 主要代码位置 | 说明 |
|---------|-------------|------|
| 层次化规则库（数据） | `catalogs/rules_catalog_top_down.json`、`catalogs/symbolic_catalog.json`、统一库产物（如 `catalogs/unified_rule_library_*.json`） | 领域 → 主题 → 规则；符号目录与规则 id 对齐 |
| 规则匹配（检索） | `core/rule_catalog_retrieval.py` | 从目录中打分并选取候选主题与规则（`unified_rules_v2` 元数据路径） |
| 语义规则检查 | `core/semantic_rule_checker.py`（`SemanticRuleChecker`） | 符号图摘要 + SRD → LLM → `diagnostics` |
| 规则检查主流程 | `core/physics_rule_verifier.py`（`PhysicsRuleVerifier`） | 串联匹配、语义检查、符号核查与结果合并 |
| 规则插件与上下文 | `rules/base.py`、`rules/llm_rules.py`、`rules/graph_consistency.py` | `RuleContext`、可扩展规则插件；语义检查器可引用内置规则映射 |
| 符号执行与目录 | `rules/symbolic_checks.py`、`symbolic/symbolic_catalog.py`、`symbolic/spec_synthesis.py`、`symbolic/experience_bank.py`、`symbolic/experience_code_engine.py` 等 | 目录查找、原语执行、经验沉淀与规格合成 |
| 一键跑检查 | `scripts/run_top_down.py` | CLI：读样本 JSON → `PhysicsRuleVerifier.verify` → 主结果 + 符号审计 JSON |
| 规则库构建与维护 | `scripts/build_unified_rule_library.py`、`scripts/merge_rules.py`、`scripts/run_semantic_experience.py`、`scripts/analyze_unified_matching.py` 等 | 合并知识/经验规则、语义蒸馏、匹配分析 |
| 经验 → 符号代码 | `scripts/translate_experience_to_symbolic.py` | 强模型生成可执行检查代码并写入 manifest / 模块 |
| 错误级测评 | `scripts/evaluate_physics_eval_sets.py`、`scripts/compute_strict_eval_metrics.py` | 与带标注错误集对齐，算 P/R/F1 |
| 题目级测评 | `scripts/evaluate_question_level_sets.py` | 整题是否误报/漏报 |
| 端到端测评编排 | `scripts/run_physics_eval_pipeline.py` | 串联构建子集、`run_top_down`、两套 evaluate 与质量审计 |

---

## 整体结构（概念分层）

项目的核心实现主要包含以下几个部分：

- **统一的规则框架**：层次化的规则库与可复用的构建/维护流程。
- **符号核查框架**：与规则对应的符号检查规格或代码，及执行与维护逻辑。
- **规则检查器**：主流程——基于规则框架检查作答，并对结果做符号核查与合并。
- **测评框架**：错误级与题目级两套指标与脚本。

## 具体实现

### 统一的规则框架

**含义**：规则生成、层次化规则库、以及离线维护工具链。

| 环节 | 对应文件 / 数据 | 流程要点 |
|------|----------------|----------|
| 规则生成（语义侧经验） | `scripts/run_semantic_experience.py` | 按目录主题对样本跑强模型，产出原始/蒸馏经验规则 JSON（如 `results/semantic_experience*.json`） |
| 规则库构建 | `rule_framework/builder.py`、`scripts/manage_rule_library.py build`、兼容入口 `scripts/merge_rules.py` | 读知识骨架、经验规则集合和 tagged 参考，构建 `domain → topic → context → cluster → rule` 树，同时保留 `topic.rules` 扁平视图 |
| 规则合并与编辑辅助 | `rule_framework/maintenance.py`、`scripts/manage_rule_library.py` | 提供 add/remove/recluster/validate/bind-symbolic 等可复用维护能力 |
| 匹配质量分析 | `scripts/analyze_unified_matching.py` | 用与线上一致的检索打分逻辑分析主题/规则命中情况 |
| 评测子集构建 | `scripts/build_physics_eval_sets.py`、`scripts/prepare_error_expansion_samples.py`、`scripts/prepare_rubric_eval_subset.py` 等 | 为错误级/题目级测评准备 JSON |

**层次化数据形态**：目录 JSON 一般为 `domains[] → topics[] → rules[]`；统一库 v2 在 `metadata.catalog_type == unified_rules_v2` 时，由 `PhysicsRuleVerifier` 走检索分支而非纯 LLM 主题分类。

#### 理想状态对应实现

- 规则生成：`scripts/run_semantic_experience.py` 对样本做语义审计，输出原始样本级错误集合和蒸馏后的经验规则集合（`rules[]`，含 `rule_id/domain/topic/title/trigger/check_logic/support/symbolic_hint`）。
- 规则库构建：`rule_framework/builder.py` 从经验规则集合构建树状层次化规则库；每个叶子节点是一条经验规则，路径字段为 `path = {domain, topic, context, cluster}`，目录中同时保存 `rule_tree` 和 verifier 可直接消费的 `topic.rules` 扁平视图。
- 相关脚本：
  - 经验规则生成脚本：`scripts/run_semantic_experience.py`。
  - 从头构建层次化规则库：`scripts/manage_rule_library.py build`；旧入口 `scripts/merge_rules.py` 保持兼容，内部调用同一套 `rule_framework.builder`。
  - 将新增经验规则添加到规则库：`scripts/manage_rule_library.py add`，底层为 `rule_framework.maintenance.add_experience_rules`。
  - 聚类、删除、校验等结构调整：`scripts/manage_rule_library.py remove/recluster/validate`，底层为 `rule_framework.maintenance` 与 `rule_framework.validation`。
- 配套工具：
  - 经验规则到符号检查代码的翻译器：`scripts/translate_experience_to_symbolic.py`，可读取蒸馏规则 JSON 或统一规则库中的规则叶子，并在 manifest 中保留 `path/symbolic_hint`。
  - 符号检查库维护脚本：`scripts/manage_rule_library.py bind-symbolic` 可将生成代码 manifest 绑定回规则叶子的 `symbolic_binding`。
  - 检查阶段规则匹配完整流程：`core/rule_catalog_retrieval.py` 提供 `topic_rule_leaves` / `iter_rule_leaves`，`core/physics_rule_verifier.py` 与 `scripts/analyze_unified_matching.py` 使用同一读取函数，保证树结构变化不会破坏线上匹配。

### 符号核查框架

**含义**：每条（类）规则对应可执行的符号检查；保证与规则库演进一致。

| 组件 | 文件 | 作用 |
|------|------|------|
| 符号检查原语与执行器 | `rules/symbolic_checks.py`（`GeneratedSymbolicCheckExecutor` 等） | 按 `primitive`+`params` 在 `RuleContext` 上执行 |
| 人工/半自动目录 | `symbolic/symbolic_catalog.py`、`catalogs/symbolic_catalog.json` | 按 domain/topic/rule 查找适用规格 |
| 规则文本 → 规格 | `symbolic/spec_synthesis.py`（`RuleSymbolicSpecSynthesizer`） | 为主题下规则合成符号检查规格 |
| 经验晋升 | `symbolic/experience_bank.py` | 将运行中提案沉淀并在满足条件时晋升入「可用规格」集合 |
| 经验代码路径 | `symbolic/experience_code_engine.py`、`symbolic/generated_experience_checks.py` | 由 manifest 绑定 `rule_id` → 确定性 Python 检查（与 README「经验代码唯一路径」一致） |
| 规格/代码生成脚本 | `scripts/translate_experience_to_symbolic.py` | LLM 生成代码并更新 manifest |

维护上，符号侧与规则侧通过 **相同的 `rule_id` / 主题路径** 对齐；运行时在 `PhysicsRuleVerifier.verify` 内合并 catalog、experience bank、合成规格及（可选）agentic 生成规格。

### 规则检查器

**含义**：对单条样本执行「匹配 → 语义检查 → 符号核查 → 结果合并」。

#### 模块分工

| 步骤 | 模块与类型/函数 | 说明 |
|------|----------------|------|
| 规则匹配 | `core/rule_catalog_retrieval.py`：`build_topic_candidates`、`score_topic_candidate`、`score_rule_candidate`、`select_rules_with_topic_priority` 等 | **Unified v2**：用题干+上下文对全库主题打分，取 Top-K 主题后再对规则打分并截断；**经典模式**：`PhysicsRuleVerifier.classify_topic` 用 LLM 从扁平主题列表中选单一主题 |
| 规则检查（语义） | `core/semantic_rule_checker.py`：`SemanticRuleChecker.analyze` | 注入当前批次的 `rule_translations`（SRD 文本），构建可选 `SymbolGraph`，逐规则调用 LLM 得 `diagnostics` |
| 符号核查 | `core/physics_rule_verifier.py` 内 `verify`：结合 `symbolic_catalog`、`spec_synthesizer`、`symbolic_executor`、可选 `_agentic_decide_symbolic_check` | 对每个 diagnostic 解析适用规格并执行，收集 `symbolic_post_diagnostics` |
| 结果合并 | 同文件 `verify` 末尾对 `diagnostics` 的循环 | 若符号结果全部为 pass 且无 fail/inconclusive，则抑制原 diagnostic（保守策略：fail/inconclusive 时保留） |
| 经验规则支线 | `verify` 中 `enable_experience_pipeline` 分支 | 按主题加载 `results/semantic_experience_distilled_*.json` 等，关键词触发后追加诊断并可跑轻量符号 spec |

#### 端到端调用链（运行时）

1. **入口**：`scripts/run_top_down.py` 解析参数 → 构造 `PhysicsRuleVerifier(...)` → 对输入列表逐条 `verify(sample)`。
2. **匹配**：若 `unified_rules_path` 指向 v2 目录则 `_retrieve_unified_v2_topics` / `_retrieve_unified_v2_rules`；否则 `classify_topic` + 当前主题 `rules`。
3. **语义**：设置 `semantic_checker.rules_to_check` 与 `rule_translations` → `SemanticRuleChecker.analyze(sample)`。
4. **符号与合并**：若有 diagnostics 且开启 agentic/上下文，构建 `RuleContext`（`rules/base.py`）→ 执行符号检查 → 按策略写回 `diagnostics` 与 `agentic.suppressed_diagnostics` 等字段。
5. **输出**：主 JSON（精简 diagnostics）与可选符号审计 JSON（`run_top_down.py` 内 `_build_symbolic_audit`）。

离线自检也可直接 `python core/physics_rule_verifier.py [data.json]`（默认写 `results/top_down_results.json`）。

### 测评框架

| 维度 | 脚本 | 输入约定 | 指标 |
|------|------|----------|------|
| 错误级 | `scripts/evaluate_physics_eval_sets.py` | 预测侧含逐条错误定位/规则引用，与标注错误集对齐 | 精确率、召回率、F1 等 |
| 题目级 | `scripts/evaluate_question_level_sets.py` | 按题聚合：错题应检出 / 对题不应误报 | 题目级 P/R/F1 |
| 严格口径汇总 | `scripts/compute_strict_eval_metrics.py` | 读 `run_top_down.py` 主输出 + 符号审计 + rubric meta | 严格集合上的指标与 inconclusive 比例等 |
| 流水线 | `scripts/run_physics_eval_pipeline.py` | 串联构建数据、`run_top_down`、evaluate、可选 `audit_eval_set_quality` | 统一输出目录下多份 JSON |

## 与历史命名的对应关系

为与上文「规则匹配 / 语义检查 / 主流程」一致，核心文件已从旧名重命名：

| 旧名 | 新名 |
|------|------|
| `core/top_down_verifier.py`（`TopDownVerifier`） | `core/physics_rule_verifier.py`（`PhysicsRuleVerifier`） |
| `core/rule_based_verifier.py`（`RuleBasedVerifier`） | `core/semantic_rule_checker.py`（`SemanticRuleChecker`） |
| `core/unified_retrieval.py` | `core/rule_catalog_retrieval.py` |

CLI 入口 `scripts/run_top_down.py` 仍保留文件名，避免已有 shell/runbook 断链；其内部已改为使用 `PhysicsRuleVerifier`。
