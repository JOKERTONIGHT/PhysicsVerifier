# 规则库规模曲线实验报告（远程 API 30B，错误级测评）

> 生成时间：2026-06-09 UTC  
> 实验批次 STAMP：`20260608_190949`  
> **分析范围**：规模点 300 / 600 / 900 / 1200 / 1500（实验于 2100 档 eval 中途手动停止）

## 实验设置

- **推理后端**：远程 OpenAI 兼容 API（Qwen3-30B-A3B-Instruct-2507，`https://yeysai.com/v1`）
- **Embedding**：`text-embedding-3-large`（同 API）
- **测评集**：`error_eval_dataset_100.json`（100 样本，688 条 GT 错误；location match）
- **规则挖掘池**：`evaluation_sample_3000_expansion.json` 非 blocked 子集（2691 样本）
- **语义经验**：复用 `catalogs/semantic_experience.json`（不在各 scale 重跑抽取）
- **规则库构建**：每 scale 完整 unified pipeline（subset → prepare-cluster 无 seed → embedding 聚类 → LLM cluster 标注 → blueprint → rebuild）
- **Verifier**：`run_verifier.py`，`--max-per-sample 12 --max-per-paragraph 2 --no-symbolic-check`
- **数据泄露防护**：error_eval 与规则池 question 零重叠；error_eval ⊆ holdout_200

## Recall 分段增益（核心结论）

| 区间 | ΔRecall | Δ命中数 | 新增规则数 | 每新增 100 条规则 Recall 增益 |
|---|---:|---:|---:|---:|
| 300 → 600 | **+3.2 pp** | +22 | +443 | +0.72 pp |
| 600 → 900 | **+2.9 pp** | +20 | +392 | +0.74 pp |
| 900 → 1200 | **−0.3 pp** | −2 | +444 | −0.07 pp |
| 1200 → 1500 | **+0.6 pp** | +4 | +460 | +0.13 pp |
| **900 → 1500（合计）** | **+0.3 pp** | **+2** | **+904 (+74%)** | **+0.03 pp** |

### 结论：900 之后 Recall 提升已不明显

1. **Recall 在 900 附近进入平台期**  
   - 600→900 仍显著上升（+2.9 pp，+20 条命中）。  
   - 900→1200 Recall **反而下降** 0.3 pp（137→135 命中），属于统计噪声范围内的波动，说明继续扩库并未带来稳定增益。  
   - 1200→1500 仅 +0.6 pp（+4 命中）；**900→1500 净增仅 +0.3 pp**，规则数却增加 74%。

2. **边际效率急剧下降**  
   - 300–900：每新增约 100 条规则，Recall 约 +0.7 pp。  
   - 900 之后：每新增 100 条规则，Recall 约 +0.03 pp（两个档位合计），**效率下降约 20 倍**。

3. **与全库 baseline 的差距主要在 900 之前已拉开**  
   - 900 档 Recall 19.9%，距全库 23.4% 差 **3.5 pp**（约 24 条 GT 错误）。  
   - 1500 档 Recall 20.2%，差距仍为 **3.2 pp**——扩到 1500 样本几乎未缩小与全库 Recall 差距。

4. **F1 在 900 后同样趋平**  
   - F1 峰值出现在 900（29.0%）与 1500（29.7%）之间，1200 略回落至 28.8%。  
   - Precision 随规模缓慢上升（58.6%→55.8% 先降后升），Recall 平台期下 F1 改善主要来自 Precision 微调，而非检出更多错误。

5. **触发率已饱和**  
   - 600 档起触发率 ≥96%，900 档 98%。Recall 瓶颈不在「LLM 不触发」，而在「规则库覆盖 / 检索 / 规则质量」——继续堆规则对 Recall 帮助有限。

## 实验停止说明

原批次计划跑至 2700（自适应 F1 停止）。在完成 1800 档后进入 2100 档 catalog 构建 + eval（约 30/100 样本）时，按分析需求**手动停止**。本报告仅采用已完成且稳定的五档（300–1500）结果；1800 档数据未纳入（Recall 21.4%，与 1500 相比 +1.2 pp，仍属 900 平台附近的小幅波动）。

## 建议

- **规则库规模**：若以 Recall 为主要目标，**900 样本 / ~1200 规则** 是性价比最高的工作点；继续扩至 1500+ 样本对 Recall 收益极小。  
- **缩小与全库 Recall 差距（3.5 pp）**：需从规则质量、cluster/blueprint 覆盖、检索排序优化入手，而非单纯增加 expansion 样本数。  
- **后续实验**：可固定 900 档规则库，对比 retrieval top-k、publish_gate、prompt 等改动对 Recall 的影响。
